# FUN60 Pro, wired Hall — dev_id 2304 (bring-up notes)

MonsGeek/Akko **FUN60 Pro** single-mode wired (`ry5088_akko_fun60pro_1m_8k`),
`dev_id` **2304**, stock **v309**. USB `3151:502d` normal, `3151:502a` RY-DFU,
`2e3c:df11` AT32 ROM-DFU. No PAN1080 radio (`wireless = false`).

**Physical USB is on the OTGHS core.** The stock app image references
`OTGHS_BASE` (`0x40040000`) only and never `OTGFS1_BASE` (`0x50000000`), and it
negotiates High Speed. So the custom build must use `-DUSB_OTG_HS` with
`USB_HIGH_SPEED_CORE_ID`: `-DUSB_OTG_FS` drives the unwired OTGFS1 PHY and the
device never appears on the bus at all (that was the entire first failure).

## Identity (measured live)

- GET_INFOR: `8F 00 09 00 00 00 00 09 03` → dev 2304, version word `0x0309` = v309
  (0.01 mm travel units, raw = mm × 100).
- `bcdDevice 3.09`, iManufacturer blank (6 spaces), iProduct `MonsGeek Keyboard`.
- Profile: `firmware/profiles/2304.toml` mirrors all of this, including the PID
  (`0x502D`, not `0x5030`).

## Stock image

```
ry-flash --fetch 2304 --stock-dir ~/ry-stock   # keeps it out of /tmp
# -> ~/ry-stock/2304/fw_at32.bin (124668 B, sha256 237bbe74…a6ac)
```

## Recovery ladder

1. Normal `3151:502d`: `ry-flash --auto --arm --stock-dir ~/ry-stock`
   (dry-run first without `--arm`).
2. Stuck in RY-DFU `3151:502a`: `ry-flash --image ~/ry-stock/2304/fw_at32.bin --arm`.
   This is also where the custom build parks itself on any bring-up failure
   (see the self-recovery net below) — a spurious trip is harmless, just run
   the restore.
3. ROM-DFU `2e3c:df11`: `sudo dfu-util -a 0 -d 2e3c:df11 -s 0x08000000:leave -D ~/ry-stock/2304/fw_at32.bin`.
   Also usable directly for the custom build:
   `make -C firmware flash-romdfu PROFILE=2304`
   (`dfu-util -a 0 -d 2E3C:DF11 -s 0x08005200:leave -D build/2304/ry5088_2304.bin`).
   Entering RY-DFU wipes config (re-set in the app); Hall cal is preserved.

## Reset policy (exactly one reset path)

Every early bring-up wait — HEXT ready, PLL/PLLU stable, sysclk switch, ADC
conversion + calibration, RGB DMA, and the "USB CONFIGURED" gate — is **bounded
and non-fatal**: on timeout that step simply gives up. A dead crystal shows up
as *no USB*, a dead ADC as *no keys*; neither ever resets the board, so a bad
build cannot loop into a reset storm.

The **only** reset in the firmware is `board_enter_dfu()`
(`firmware/common/board.c`), reachable solely from the host's
`0x7F 55 AA 55 AA` enter-bootloader handshake in `main.c`. It writes **two**
single-word flash markers — the boot-mailbox magic `0x55AA55AA` at `0x08004800`
*and* an invalid chip-ID at `0x08005000` — then resets. Both are word programs
(no erase), the resident bootloader at `0x08000000`–`0x08004FFF` is never
touched, and the pair guarantees the bootloader parks in HID-DFU (`3151:502a`)
so step 2 of the ladder restores stock with no case-opening.

> **The bug that broke restoration:** a bare `NVIC_SystemReset()` with no
> mailbox write makes the bootloader simply re-enter the app — the host never
> sees `502A`, so every flash appeared to "only restart". Our pre-v11 builds
> did exactly this on `0x7F`. The mailbox **plus** chip-ID pair above fixes it.

## Build identity marker (custom vs stock)

The custom build reports a **different identity** from stock so you can always
tell which firmware is running — necessary because both otherwise present as
`dev_id 2304`:

| | stock v309 | custom build |
|---|---|---|
| `lsusb` `bcdDevice` | `3.09` | **`4.00`** (`bcd_device = 0x0400`) |
| `ry-flash --detect` version | `v309` | **`v400`** (`[version]` hi/lo) |

`PID` (`0x502d`), `dev_id` (`2304`), the strings and the three HID interfaces
are deliberately identical to stock so the vendor app and `iot-driver` keep
working. Reporting a *higher* version also stops the vendor app from offering
a "firmware update".

## Rapid Trigger

Stock v309 is **continuous RT by construction** (see the driver repo's
`docs/FUN60_PRO.md` §6 and Akko's "continuous RT" note): after the first
actuation the whole travel stays ready until full release.

This firmware implements **both**, per `common/hall.c`:

- `traditional` — the trigger zone is only below the actuation point; rising
  above it resets and disarms, so the next trigger must re-cross actuation.
- `continuous` — stock CRT semantics.

The profile default ships `traditional` (`[hall] rt_mode`, emitted as
`HALL_DEF_RT_MODE`). The vendor-app RT toggle (mode-byte `0x80`) keeps the
vendor behaviour it can express; the *flavour* is a global firmware extension
byte (`cfg[0x1F]`), persistent across reboots:

- `SET_RTMODE 0x1F [flavour]` / `GET_RTMODE 0x9F -> [flavour]`
  (`0` traditional, `1` continuous). Stock firmware does not answer these; a
  read there only echoes the opcode.

CLI (see the sibling `monsgeek-akko-linux` repo, `iot_driver`):

```
iot_driver rt-flavour                   # read (traditional|continuous)
iot_driver rt-flavour traditional        # switch to classic RT
iot_driver rt-flavour continuous        # switch back to stock CRT
```

Host proof: `firmware/common/test/test_engine.c` §2c drives the same key
stroke under both flavours and asserts they diverge exactly as specified.
